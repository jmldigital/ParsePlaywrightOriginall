# Stparts Price API

Новый сервис цен **только Stparts**, ветка `codex/stparts-price-api`, база — `main` / `6ae632e`.
Стек: Python 3.12, FastAPI, Uvicorn, Playwright Chromium, SQLite WAL, uv, Docker.
Старый Excel-сценарий сохранён в `legacy/` для сравнения. Новый сервис его не импортирует;
входной цены и вызова `price_adjuster.py` нет. Legacy-зависимости в новое окружение не входят.

## Запуск на сервере

План размещения: отдельный контейнер `stparts-price-api` на вашем Linux-сервере,
папка `/opt/Parce_Price_Api`, постоянный Docker volume `stparts-api-data` для SQLite.
Выбран адрес `http://pricess.avpvl.ru:8080`, без TLS на текущем этапе.
Django на порту 1337 и страница логов на порту 80 остаются без изменений.
Удалённое развёртывание ещё не выполнено.

```sh
git clone --branch codex/stparts-price-api https://github.com/jmldigital/ParsePlaywrightOriginall.git /opt/Parce_Price_Api
cd /opt/Parce_Price_Api
cp .env.example .env
# Заменить API_TOKEN случайным секретом, заполнить CAPTCHA_API_KEY.
docker compose up -d --build
docker compose logs -f stparts-price-api
curl http://127.0.0.1:8000/health
```

Сервис доступен серверному Nginx на `127.0.0.1:8000`. HTTP-конфигурация
для выбранного порта 8080 подготовлена в `deploy/nginx-price-api.conf`.
После успешного локального `/health` установите её отдельным файлом
(если такой файл уже существует, сначала проверьте его содержимое):

```sh
sudo cp deploy/nginx-price-api.conf /etc/nginx/sites-available/stparts-price-api
sudo ln -s /etc/nginx/sites-available/stparts-price-api /etc/nginx/sites-enabled/stparts-price-api
sudo nginx -t && sudo systemctl reload nginx
curl http://127.0.0.1:8080/health
```

Проверьте с другого компьютера `http://pricess.avpvl.ru:8080/health`.
Если локальная проверка успешна, а внешняя нет, проверьте разрешение входящего
TCP 8080 в firewall сервера и хостинга. Порт 8000 наружу не открывается.
HTTP не шифрует токен и результаты; это согласованный режим текущего этапа.

Swagger: `/docs`, OpenAPI: `/openapi.json`. Методы `/jobs` требуют Bearer-токен;
`/health` и описание API не содержат данные заданий и доступны без токена.
Один токен обозначает одного клиента: все задания сервиса доступны его владельцу.

**Один контейнер и один процесс Uvicorn.** Не используйте `--workers > 1`,
`--reload` в production или несколько реплик на одной БД. Межпроцессный file lock
запрещает запуск второго экземпляра, чтобы он не сбросил состояние работающих позиций.
SQLite должен лежать на локальном диске сервера, не на сетевом/синхронизируемом диске.
Docker-volume сохраняется при пересоздании контейнера; `docker compose down -v` удалит данные.

## Режим браузера в Docker

Контейнер запускает Chromium с виртуальным экраном Xvfb (`HEADLESS=false`).
В живой проверке Stparts режим без окна зависал, а режим с экраном получал предложения.
Физический монитор на сервере не нужен. Сохраняйте `init: true` в Compose;
при ручном `docker run` добавляйте `--init`. Не задавайте `HEADLESS=true` в `.env`
для этого сценария без отдельной проверки доступности источника.
Автоматическая страница проверки браузера может возвращать HTTP 403: сервис ждёт
результаты только при распознанной странице проверки; обычный 403 остаётся ошибкой.
После изменения кода используйте `docker compose up -d --build`, а не `start`.
Уже завершённые позиции с ошибками автоматически не повторяются: для повторного
теста задайте новый `batch_id`.

## Контракт

```http
Authorization: Bearer <API_TOKEN>
Content-Type: application/json
```

- `POST /jobs`: JSON как в `examples/batch.json`; 1–500 позиций; немедленно `202` с
  `job_id`, `batch_id`, `status`, `total`. Данные фиксируются в БД до ответа.
- `GET /jobs/{job_id}`: статус, total, processed, found, not_found, errors.
- `GET /jobs/{job_id}/results`: исходные id/brand/oem, status, price, currency,
  delivery_days, parsed_at, error. До завершения выдаёт только обработанные позиции;
  после завершения — все, в исходном порядке. `expires_at` задан после завершения.
- `id` и `batch_id` — строки, непустые, до 128 символов; id уникален внутри батча.
- `max_delivery_days`: целое 0–365, по умолчанию 2, включительная верхняя граница.
- Цена — десятичная строка, например `"123.40"`, RUB; отсутствующая цена/срок — null.
- Даты — ISO 8601 UTC (`Z`). parsed_at означает завершение попытки обработки позиции.
- Статусы позиции: found / not_found / error. Ошибка позиции не прерывает задание.
- Статусы задания: queued / running / completed; failed зарезервирован для
  терминальной ошибки задания. Ошибки позиций входят в completed с ненулевым errors.
- Пока батч хранится, одинаковый batch_id и одинаковый запрос возвращают прежний job_id.
  Изменение содержимого (включая порядок) при том же batch_id → 409.
- 401: нет/неверный токен; 422: неверные поля, пустой батч, >500 или дубликаты id;
  429: очередь заполнена; 404: неизвестное/истёкшее задание; 503: обработчики недоступны.
- Неизвестные входные поля запрещены: случайная входная цена не игнорируется молча.

```sh
curl -X POST http://127.0.0.1:8000/jobs -H "Authorization: Bearer $API_TOKEN" -H 'Content-Type: application/json' --data-binary @examples/batch.json
curl http://127.0.0.1:8000/jobs/JOB_ID -H "Authorization: Bearer $API_TOKEN"
curl http://127.0.0.1:8000/jobs/JOB_ID/results -H "Authorization: Bearer $API_TOKEN"
```

## Очередь и восстановление

Каждый батч имеет максимум **две** активные позиции. GLOBAL_CONCURRENCY=2 ограничивает
весь сервис двумя позициями; несколько батчей делят лимит, очередной выбирается по
времени последней выдачи позиции. Для проверки параллельных батчей можно поставить 4,
но только после нагрузочного теста реального источника. На каждый HTTP-запрос не создаётся
отдельный браузер/500 задач: фиксированное число обработчиков читает SQLite.

Результат сохраняется после каждой позиции. После рестарта только running-позиции
становятся pending; готовые результаты не перепарсиваются. Если процесс упал после
запроса к Stparts, но до записи результата, эта позиция будет запрошена ещё раз
(at-least-once). У каждого поиска есть таймаут ITEM_TIMEOUT_SECONDS (по умолчанию 180).
Контекст и страницы закрываются после позиции, браузер переиспользуется и запускается
заново после отключения. Контексты изолированы, чтобы не копить память на тысячах строк.

TTL — **50 часов после завершения задания**. GET скрывает истёкшие задания сразу,
физическая очистка с каскадным удалением позиций выполняется каждые 5 минут.
Активные задания не чистятся. Предел очереди MAX_ACTIVE_JOBS=100 (до 50 000 позиций).
При неисправности БД обработчик останавливается и `/health` возвращает 503;
настройте оповещение/перезапуск в серверном мониторинге: Docker healthcheck сам
по себе не перезапускает unhealthy-контейнер. После перезапуска очередь восстанавливается.

## Правила Stparts

Переиспользованы маршруты поиска, DOM-селекторы, сопоставление слов бренда,
резервный поиск по OEM и схема отправки капчи из исходного проекта.
Выбирается **минимальная** цена среди строк совпавшего бренда с допустимым сроком,
при одинаковой цене — меньший срок. Диапазон `1–3` сравнивается с лимитом по нижней границе 1.
При лимите 2 дня предложения `1–3` и `1–4` учитываются; `3–4` исключается.
В `delivery_days` возвращается нижняя граница — для `1–3` это 1, а не гарантированный срок.
`в наличии`/`сегодня` → 0. Неизвестный формат цены/срока у совпавшего бренда → error,
а не ложное not_found. Таймауты/ошибки источника тоже не маскируются под отсутствие товара.
Срок берётся как число дней, указанное источником; пересчёта рабочего календаря нет.

CAPTCHA_API_KEY — ключ 2Captcha, не клиентский API_TOKEN. Решение капчи использует
платный внешний сервис только при реальном запуске с ключом. Без ключа капча →
CAPTCHA_REQUIRED. При необходимости сессии STPARTS_STORAGE_STATE указывает на
Playwright storage_state JSON, который нужно отдельно примонтировать read-only.
Логика авторизации Avtoformula из legacy не используется для Stparts.

## Разработка и проверки

```sh
uv sync --frozen
uv run uvicorn price_api.app:create_app --factory --host 127.0.0.1 --port 8000
uv run pytest -q
uv run ruff check price_api tests
```

Зависимости зафиксированы в uv.lock; Docker использует `uv sync --frozen --no-dev`.
Версии Playwright в Python и базовом образе совпадают (1.58.0).
Тест планировщика использует имитацию источника и SQLite в памяти: три батча по 500.
Отдельные тесты файловой SQLite проверяют ошибки, таймауты,
идемпотентность, ограничения параллельности, восстановление и TTL.
Это не подтверждает реальную скорость/устойчивость Stparts. До production нужен
пробный реальный батч и затем два батча по 500 с контролем памяти, капчи и сроков.

## Логи парсинга в реальном времени

```cmd
docker compose logs -f --tail=100 --timestamps stparts-price-api
```

`parse_start` — начало позиции: job_id, id, бренд, артикул и лимит срока.
`parse_done` — сохранённый результат: статус, цена, нижняя граница срока,
код ошибки и длительность обработки. Две позиции могут обрабатываться одновременно;
сопоставляйте строки по job и id. Ctrl+C закрывает просмотр, сервис продолжает работу.
Токены и ключи сервиса решения капчи в эти сообщения не записываются.

## Диагностика капчи и ответов источника

При HTTP-ошибках, ошибках капчи и тайм-аутах загрузки сервис сохраняет
в `/app/data/diagnostics` JSON с URL, временем и HTTP-статусом, HTML отображаемой
страницы и PNG видимой области. При зависшей странице снимок может не получиться;
ошибка диагностики не заменяет исходную ошибку позиции. HTML очищается от script
и введённых значений input/textarea, поля ввода маскируются на PNG. Это служебные
материалы: не публикуйте папку через Nginx. HTTP-заголовки, cookies и ключи
провайдера отдельно не экспортируются.

По умолчанию сохраняются последние 20 комплектов (при прерванной записи возможен
один дополнительный неполный комплект). Они находятся в постоянном Docker volume.
`DIAGNOSTICS_ENABLED=false` отключает сбор, `DIAGNOSTICS_MAX_SAMPLES` задаёт лимит.
Новые настройки имеют значения по умолчанию, существующий `.env` менять необязательно.

В журнале видны `source_navigation`, `captcha_detected`, `captcha_submit`,
`captcha_solution_received`, `captcha_accepted`, `captcha_provider_rejected`
и `source_diagnostic`. Код `ERROR_ZERO_BALANCE` означает отказ провайдера
из-за баланса; эта запись не означает блокировку источником. Ключи и ответы
решённой капчи не печатаются. Поддерживается прежняя картинка `img.captchaImg`;
другие виды проверки браузера не считаются автоматически решаемой капчей.

Скопировать диагностику из контейнера в папку проекта на сервере:

```sh
cd /home/Parce_Price_Api
mkdir -p data/server-diagnostics
docker cp stparts-price-api:/app/data/diagnostics/. ./data/server-diagnostics/
docker compose logs --no-color --tail=300 stparts-price-api > ./data/server-diagnostics/container.log
```

Скачайте папку `data/server-diagnostics` через MobaXterm. Для проверки сначала
отправьте небольшой батч с новым `batch_id`; не повторяйте непрерывно большой батч
при серии HTTP 403. Эти файлы позволяют отличить запрет доступа от капчи и ошибки
распознавания страницы. Сам по себе код 403 причину не доказывает.
