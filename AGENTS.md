## Контракт API

POST /jobs принимает batch_id, max_delivery_days (по умолчанию 2), parts (от 1 до 500 позиций). Каждая позиция: id, brand, oem. Идентификаторы позиций должны быть уникальны внутри батча.

Ответ 202 содержит job_id, batch_id, status, total. Это принятие задания, а не его завершение.

GET /jobs/{job_id} возвращает актуальный статус и счётчики total, processed, found, not_found, errors.
GET /jobs/{job_id}/results возвращает доступные результаты. Сохраняется пользовательский id; результат содержит статус, цену, срок в днях, дату парсинга, сведения об ошибке при её наличии.

Статусы позиций: found, not_found, error. Не заменять техническую ошибку на not_found.
Повторный batch_id с тем же содержимым возвращает существующее задание; с другим содержимым — 409. Для независимого теста нужен новый batch_id.

Маршруты заданий защищены Authorization: Bearer. /health и /docs доступны без этого заголовка. /docs — стандартный Swagger UI FastAPI. Прямое открытие защищённого URL в браузере без заголовка даёт 401; это не ошибка парсинга источника.

## Прохождение задания

1. API проверяет вход и авторизацию, сохраняет задание в SQLite.
2. Runner получает позиции через Store.claim.
3. Работник вызывает StpartsScraper.search для одной позиции.
4. Парсер открывает страницу, определяет её состояние, читает предложения и выбирает подходящее.
5. Результат или ошибка сохраняется через Store.finish сразу после позиции.
6. Клиент опрашивает прогресс и результаты; соединение клиента не требуется на всё время обработки.

По умолчанию GLOBAL_CONCURRENCY=2 на весь сервис, а не по два дополнительных браузера на каждый батч. Выдача работы ограничивает параллельность одного задания двумя позициями. Изоляция ошибок относится к позициям; ошибка БД может остановить работника и сделать health нездоровым.

ITEM_TIMEOUT_SECONDS по умолчанию 180. Превышение становится SOURCE_TIMEOUT. Прерванные running-позиции восстанавливаются при запуске; уже записанные ошибки не превращаются автоматически в новые попытки.

## Выбор предложения и сроки

Сопоставление бренда основано на пересечении нормализованных токенов, а не на полном каталоге производителей. Это существующее правило, не гарантия отсутствия ложных совпадений.

Цена разбирается в Decimal, выдаётся строкой с двумя знаками. Среди подходящих предложений выбирается минимальная цена; при равной цене — меньший срок.

По явно согласованному правилу диапазон 1–3 или 1–4 дня считается как 1 день и подходит при max_delivery_days=2. Это нижняя граница, не гарантия доставки максимум за два дня. «В наличии»/«сегодня» — 0 дней.

Неизвестный формат цены или срока у строки с подходящим брендом может дать SOURCE_FORMAT, даже если есть другие читаемые строки: нельзя достоверно выбрать минимум, игнорируя потенциально более дешёвую строку.

## CAPTCHA и reCAPTCHA: текущая реализация и ограничения

Это разные состояния страницы, их нельзя считать одной капчей. Проверка браузера источником также является отдельным состоянием.

В stparts.py метод _read_page после навигации ожидает одно из состояний: предложения, отсутствие результатов, изображение CAPTCHA или форма reCAPTCHA. Затем выбирает соответствующий обработчик. read_page оборачивает чтение диагностикой ошибок.

В stparts.py существуют solve_captcha и solve_recaptcha. Первый относится к изображению с символами, второй — к reCAPTCHA v2. Оба используют общий провайдерский помощник provider_solution: POST на `CAPTCHA_API_URL/in.php` и опрос `res.php` в пределах бюджета `CAPTCHA_SOLVE_TIMEOUT_SECONDS`, интервал опроса `CAPTCHA_POLL_INTERVAL_SECONDS`, число попыток `CAPTCHA_MAX_ATTEMPTS`, ожидание страницы `CAPTCHA_WAIT_SECONDS`. По умолчанию адрес — `https://rucaptcha.com`, методы `userrecaptcha` для reCAPTCHA v2 и `base64` для картинки. Ключ передаётся только в теле POST, чтобы не попадать в журнал URL. Решение сериализовано общим `captcha_lock`: одновременно решается только одна капча. Картинка, у которой сайт ещё не подставил `src` (собственная проверка браузера abcp), провайдеру не отправляется — это `CAPTCHA_FORMAT`. Страница ограничения доступа abcp (`Access Restricted`, `check*.nodacdn.net`) распознаётся отдельно и даёт `SOURCE_BLOCKED`.

Что выявлено при сравнении со старым проектом:

- Parse -old/utils.py содержит общий обработчик картинки с повторными попытками.
- Parse -old/captcha_manager.py ограничивает число одновременно обрабатываемых капч.
- Существовавшая в старом utils.py ветка reCAPTCHA предназначена для Adeo, не для STparts.
- Следовательно, прежняя успешная работа старого проекта не подтверждает поддержку нынешней reCAPTCHA STparts.

Наблюдения локального теста:

- STparts действительно показал сообщение о суточном лимите поиска и форму reCAPTCHA.
- Внешний сервис ранее отверг прежний 49-символьный ключ: ERROR_WRONG_USER_KEY. Это ошибка учётных данных внешнего сервиса, не доказательство неправильного распознавания страницы. Локальный ключ из 32 символов проходит проверку баланса на rucaptcha.com, 2captcha.com и api.rucaptcha.com.

## Логи, хранение и эксплуатация

Для чтения текущих логов: docker compose logs -f --tail=100 stparts-price-api.
События parse_start/parse_done связываются по job, ordinal и пользовательскому id. source_navigation и source_diagnostic помогают отличить HTTP-ошибку, таймаут и состояние страницы. Сообщение о получении ответа внешнего сервиса не равно принятию ответа источником.

Диагностика включена по умолчанию, лимит 20 наборов. Файлы записываются рядом с БД в diagnostics/: JSON с контекстом ошибки, HTML и снимок экрана при возможности. Сохранение ограничено по времени; отсутствие PNG не доказывает отсутствие ошибки. Маскирование полей не гарантирует обезличивание всей страницы.

Контейнер хранит БД в /app/data/jobs.sqlite3. /app/data подключён к именованному Docker volume stparts-api-data (обычно parce_price_api_stparts-api-data). Поэтому файл не обязан быть виден в папке исходников. Перезапуск и пересборка с сохранением volume не удаляют БД. docker compose down -v удаляет volume — не применять для обычного перезапуска.

Завершённые задания очищаются после 50 часов; период очистки по умолчанию 300 секунд. Для согласованной копии SQLite использовать механизм backup; копирование одного .sqlite3 без WAL может дать устаревший снимок.

Один процесс Uvicorn и один экземпляр сервиса на эту БД. Не увеличивать число Uvicorn workers: есть файловая блокировка и восстановление очереди.

### Что сделано в коде

price_api/stparts.py:

- Константы состояний: `RESULTS`, `CAPTCHA`, `CAPTCHA_PANEL`, `CAPTCHA_INPUT`, `CAPTCHA_SUBMIT`, `CAPTCHA_RELOAD`, `CAPTCHA_STATE` (видимые панель/поле/картинка), `RECAPTCHA_FORM`, `RECAPTCHA_FRAME`, `RECAPTCHA` (видимый виджет), `RECAPTCHA_PRESENT` (форма или виджет есть в DOM), `BROWSER_CHECK`, `BLOCKED`, `BLOCKED_HOST`.
- `captcha_key()` — отказ `CAPTCHA_REQUIRED` без ключа и предупреждение `captcha_key_length_unexpected` при длине ≠ 32.
- `captcha_endpoint()`, `captcha_deadline()`, `before()` — адрес провайдера из настроек и единый бюджет времени на все попытки.

- `recaptcha_sitekey()` — ожидание виджета до `CAPTCHA_WAIT_SECONDS`; sitekey из `data-sitekey` или из `k=` в src anchor-iframe; устойчиво к перезагрузке страницы и к `PlaywrightError`.
- `submit_recaptcha_token()` — нативный setter для `g-recaptcha-response`, события `input`/`change`, затем submit формы (кнопка, иначе `requestSubmit`).
- `recaptcha_present()`, `image_captcha_present()`, `captcha_present()`, `results_present()` — раздельные проверки состояний вместо одной проверки видимости.
- `blocked()` — распознавание страницы «Access Restricted» по тексту или по хосту `nodacdn.net`.
- `wait_for_results()`, `wait_for_captcha_image()` — ожидание результатов и реальной загрузки картинки (`complete` и `naturalWidth > 0`).
- `solve_captcha()` — картинка методом `base64`, до `CAPTCHA_MAX_ATTEMPTS` попыток, обновление кода через `a.captchaReload`, сохранение сессии при успехе.
- `solve_recaptcha()` — `userrecaptcha` с `googlekey`, `pageurl`, `userAgent`; повтор при отказе источника в пределах бюджета; сохранение сессии; если вместо капчи отрисовались результаты — `captcha_not_required` без оплаты.
- `store_source_state()`, `adopt_source_state()` — сохранение пройденной сессии и её переиспользование ожидающим воркером (`captcha_session_reused`).
- `captcha_lock` — одновременно решается одна капча (повторяет ограничение из Parse -old/captcha_manager.py).
- `_read_page(page, url, state_version)` — карта состояний, ожидание состояния, цикл обработки капч, коды `SOURCE_BLOCKED`, `SOURCE_CONNECTION_ERROR`, `SOURCE_HTTP_ERROR`.
- `read_page()` и `search()` — передача версии сессии в контекст позиции.
- `log_provider_error()` — в журнал попадает только код вида `ERROR_*`, не ответ провайдера.

### Ошибки, которые были допущены и как закрыты

1. `ERROR_WRONG_USER_KEY` при рабочем балансе RuCaptcha. Причина: в контейнерном `.env` ключ был 49 символов при ожидаемых 32; код при этом ходил на 2captcha.com. Локальный 32-символьный ключ проходит баланс на `rucaptcha.com`, `2captcha.com` и `api.rucaptcha.com`. Исправление: адрес провайдера — настройка `CAPTCHA_API_URL` (по умолчанию RuCaptcha), предупреждение о длине ключа, метод `userrecaptcha` по официальной документации.
2. 96 × `SOURCE_HTTP_ERROR` в первом реальном прогоне 200 позиций. Причина: при HTTP 403 источник отдаёт форму лимита раньше, чем Google отрисует виджет; проверка видимости капчи не срабатывала, и код сразу поднимал ошибку. Исправление: наличие формы (`RECAPTCHA_PRESENT`) проверяется отдельно от видимости виджета, sitekey ожидается, а при появлении результатов капча не решается вовсе. Это был дефект кода, а не блокировка источником.
3. `PlaywrightError: Unexpected token "="` — `text=Access Restricted` нельзя подмешивать в общий CSS-список селекторов. Исправление: страница ограничения проверяется отдельным методом `blocked()` до и после ожидания состояния.
4. Ключ провайдера попадал в журнал: httpx логирует полный URL, а `res.php` вызывался GET с `key` в query (в логе 16 вхождений ключа). Исправление: `res.php` через POST, ключ только в теле; в live-скрипте логгер `httpx` приглушён до WARNING.
5. Сценарий «картинка не загрузилась» давал `SOURCE_HTTP_ERROR` вместо `CAPTCHA_FORMAT`: пустой `div#captcha` без содержимого не считается видимым. Исправление: мок приведён к реальной странице (панель со ссылкой и полем), а признаком капчи стали панель и поле, а не только `img.captchaImg`.
6. Второй воркер, дождавшись лока, платил за ту же капчу повторно. Исправление: `adopt_source_state()` — под локом сравнивается версия сессии, свежие cookies применяются к контексту и страница перезагружается; в прогоне это дало 10 переиспользований из 23 обнаружений.
7. Скрипт наблюдения падал с `KeyError: 'items'` — в ответе `/jobs/{id}/results` поле называется `parts`; кроме того он считал задание завершённым при `status != "running"`, а сразу после POST статус `queued`. Исправление: `DONE = {completed, failed}`, повторный запуск переиспользует `job.json` вместо новой отправки.
8. Обрезка строк в `api.log`: `uvicorn ... 2>&1 | Tee-Object` в PowerShell режет длинные строки, из-за чего `parse_done ... error=...` терял код ошибки. Для точных кодов брать `diagnostics/*.json` и `results.json` либо писать stderr напрямую в файл.
9. `HEADLESS=true` → Chromium получает «Access Restricted» вместо капчи; headed-Chromium ту же проверку проходит. Исправление: для реальных прогонов обязателен `HEADLESS=false` (в Docker уже задан).
10. `SOURCE_ERROR` с трейсбеком `Page.goto: net::ERR_CONNECTION_RESET` на втором URL — необработанное исключение Playwright. Исправление: код `SOURCE_CONNECTION_ERROR` без трейсбека; такие отказы источника остаются в статистике как реальные ошибки.
11. Ошибки окружения этого сеанса: Docker Desktop не запущен, поэтому API поднимали `uvicorn` с отдельной БД (`data/local-200b`), чтобы не возобновить очередь на 250 позиций; Playwright 1.58 требовал `chromium-1208`, был только 1178 — доустановлен; DSH-песочница не могла выдать запись в папку проекта на Yandex.Disk (починено правами), а Playwright под песочницей не запускается из-за запрета piped stdio — проверки запускались с полным доступом.

### Что важно помнить следующему агенту

- Не считать `:visible` единственным признаком капчи: форма и панель появляются раньше виджета Google.
- Проверять коды ошибок по `results.json` и `diagnostics/*.json`, а не по обрезанному PowerShell-логу.
- Перед длинным реальным прогоном проверять состояние источника малым набором (`local-captcha-verified.json`) и обязательно `HEADLESS=false`.
- Не запускать сервис с боевой БД ради теста: он возобновит очередь; для тестов задавать отдельный `DATABASE_PATH`.
- Провайдерские вызовы делать только POST, ключ не должен попадать в URL и в журнал.
- Не заявлять «капча решена» по факту `captcha_solution_received`: подтверждение — `captcha_accepted` после появления результатов поиска.
